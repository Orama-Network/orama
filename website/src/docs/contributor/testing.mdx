# Testing

Every code change ships tests. This page covers the three layers: unit tests, the end-to-end cluster guide, and the fleet e2e suite that gates a release, and the rules each follows. It also describes the chain's load and saturation tests (`make -C chain bench-load`).

## Unit tests

```bash
cd core
make test                                  # go test -v ./...
go test ./pkg/path/to/package/...          # one package
go test ./pkg/path/... -run TestName       # one test
go test -race ./pkg/path/...               # race detector
```

`make test` from the repository root is the full local gate: the core Go tests, the chain's pure-Go unit tests (`make chain-test`), the Caddy module tests, the TypeScript SDK unit tests (`make sdk-test`), the fleet-e2e lint, coverage gate and harness unit tests, and the whitepaper checks. The SDK tests need `sdk/node_modules`; when it is missing the target stops with a message, and `cd sdk && pnpm install --frozen-lockfile` fixes it. The SDK tests read the gateway's Go source (for example the auth error codes in `sdk/tests/unit/auth-codes-parity.test.ts`), so a gateway change that adds a code fails them until `sdk/src/errors.ts` names it. The **e2e coverage gate** is described below. `make -C core lint`, `cd chain && make test && make lint`, `cd sdk && pnpm test`, `cd vault && zig build test`. The chain's other checks (race detector, static analysis, Rust) are described under [CI](#ci).

### What a change needs

- At least one happy-path test, one error-path test and one edge case (empty input, nil, zero value, boundary).
- A bug fix needs a test that reproduces the bug. If you deleted your implementation, a test should fail.
- Test behaviour, not implementation. Name tests `Test{Function}_{scenario}` (for example `TestGetWGPeers_empty_table`). Config or template-only changes do not need tests.
- Edge cases to consider every time: empty slices, nil maps and pointers, zero values, missing fields in a request, races in concurrent code, timeouts and refused connections, expired or invalid tokens, state after a restart.

### Patterns

- **Table-driven tests** for many inputs. Interfaces for dependencies so a fake can stand in; the clients (`NetworkClient`, `StorageClient`, `DatabaseClient`, `PubSubClient`) are interfaces for this reason.
- **Real SQLite, real behaviour.** A gateway SQL guard test asks a real SQLite whether it reads a protected table. A migration round-trip test (`go test ./migrations/`) applies every embedded migration and exercises representative SQL, so a Go handler that references a column no migration creates fails at review time. When adding a platform table: write the migration, update the Go code, add an exemplar to `migrations/roundtrip_test.go`, and place the table in the schema placement list (a test fails if a table is left unplaced).
- **The generated references are tests too.** The CLI reference (whitepaper appendix D, `docs/whitepaper/technical-reference/appendices/d-cli-reference.md`) is checked against the cobra tree, and the API surface (appendix I, `docs/whitepaper/technical-reference/appendices/i-api-surface.md`) against the registered gateway routes, in both directions. Adding a command or a route fails the build until the doc is regenerated or updated.
- **Benchmarks have a gate.** The chain's Go microbenchmarks run with `cd chain && make bench` and fail a release when one is more than 25% slower (`make bench-compare`); the fleet e2e features `perf` (gateway and data plane) and `chain-perf` (blocks, transfers, CheckTx) record baselines and compare them with the previous run's. See [Performance](/docs/contributor/performance).
- **Files above the module go through `testdata/repo`.** Go's test cache reuses a passing result while the test binary, the environment variables the test read and the files it opened inside its module are unchanged. A file outside the module is not an input, so a test that read `../../../chain/...` directly passed from the cache after that file changed. Each module (`core`, `chain`, `e2e`, `os/agent`) has a `testdata/repo/` directory of symbolic links to the repository paths its tests read (`core/testdata/repo/contracts -> ../../../contracts`, `chain/testdata/repo/core/pkg/constants`, ...), and a test reads such a file only through it. Link the narrowest directory that works and never a module root or the repository root, so no link leads back into the module holding it. `filepath.Walk` and `WalkDir` do not descend into a link given as their root; walk it with `fs.WalkDir(os.DirFS(dir), ".", ...)`. What a test hands to another process (a script `bash` runs, a tree `go list` or `protoc` reads) is not seen either: the test opens those files itself (`chain-deploy.sh` in `e2e/harness/provision`, `gen.sh` in `core/pkg/chainread`, the `go list` packages in `core/cmd/orama/internal/build`).
- **Timing is not synchronisation.** A test waits for the event it needs (a channel, a status change it subscribed to, the goroutine or process it started), never for a sleep or a wall-clock window. Code with a timeout takes its clock from the caller, so a test drives time itself: `core/pkg/ipfs` gives `GetStored`'s idle watchdog a fake clock. A test leaves nothing running: wait for the goroutines and processes it started before it returns.
- **Verify on the live system, not only in unit tests.** RQLite is not SQLite: query the live cluster and read gateway logs.

## Cluster guide e2e

The [Run your own cluster](/docs/operator/run-your-own-cluster) page is a promise that a stranger can go from bare
machines to a working private cluster with no manual SQL. `core/e2e/clusterguide`
keeps it by executing the page: it parses the page's command blocks and runs them
in order (install the first node, print the delegation, join two more,
`orama network use`, `orama auth login`, `orama namespace create`, sign in to the
namespace, `orama deploy static`, then `orama status --json` and `orama app
list`), substituting the page's example addresses, domain, environment and
release (version, repository and root) with the fixture's. A fixture given a build
archive instead has the three release flags of each `orama node setup` replaced by
`--archive`. It checks the results: the delegation output names
your domain, all three nodes report `healthy`, and `www` is listed.

The page and the executed steps cannot drift. `Plan()` in
`core/e2e/clusterguide/plan.go` lists every command the page must contain, with
the flags each needs; `TestPlanMatchesTheGuideOnDisk` runs in `make test`, with no
machines, and fails when the page gains, loses, reorders or renames a command,
drops a needed flag, or introduces an example value the fixture cannot bind.
The parser and the step runner are unit-tested against a fake executor.

The run against machines is behind the `e2e_cluster` build tag and skips unless
`E2E_CLUSTER_BASE_DOMAIN` is set. It installs Orama on the servers you name, so it
is not part of `make test`; you run it:

```bash
E2E_CLUSTER_IPS=<ip1>,<ip2>,<ip3> \
E2E_CLUSTER_BASE_DOMAIN=<a domain whose NS you can publish> \
E2E_CLUSTER_RELEASE=<a published version> \
E2E_CLUSTER_RELEASE_REPO=<the release repository's https URL> \
E2E_CLUSTER_RELEASE_ROOT=<its root.json> \
make e2e-cluster
```

To install a build of your own instead of a release, give
`E2E_CLUSTER_ARCHIVE=<the path orama maint build printed>` and none of the three release
variables; a fixture with both is refused. The release run is the path the page
describes (no checkout on the machine that types it).

| Variable | Purpose |
|----------|---------|
| `E2E_CLUSTER_BASE_DOMAIN` | The domain the cluster is named under (required) |
| `E2E_CLUSTER_IPS` | Three or more bare Linux machines, comma separated; the first is the genesis nameserver |
| `E2E_CLUSTER_RELEASE`, `E2E_CLUSTER_RELEASE_REPO`, `E2E_CLUSTER_RELEASE_ROOT` | A published release, its repository and the TUF root to verify it against; all three together. `go run ./cmd/testtuf` (in `core/`) makes a test repository and root |
| `E2E_CLUSTER_ARCHIVE` | Instead of a release: a build archive, signed by the RootWallet account that is unlocked (`orama maint build`) |
| `E2E_CLUSTER_ENV` | Environment name to create (default `e2eguide`; the page's `mycluster` is replaced by it) |
| `E2E_CLUSTER_CLOUDFLARE_TOKEN_FILE` | Optional. Runs the page's `--cloudflare-token-file` step; without it the delegation must already exist |
| `E2E_CLUSTER_DELEGATION_WAIT` | How long to wait for the NS records and the genesis certificate (default `20m`) |
| `E2E_CLUSTER_HOST_KEYS` | Optional SSH fingerprints (`SHA256:...`), one per IP; without them the harness reads each machine's with `ssh-keyscan` |
| `E2E_CLUSTER_MODE` | `full` (default) or `use-only` |
| `E2E_CLUSTER_ORAMA` | The `orama` binary (default: built into `core/bin/orama`) |

Before running: the RootWallet desktop app open and unlocked, and a vault login
for each machine (`rw vault add <ip>`), because the page's `orama node setup`
uses `--password`. The harness never types a secret and never runs `rw`. The page
installs with `--acme-ca letsencrypt-staging`, so no production certificate quota
is used. The run records the environment in `~/.orama` and makes it the active one
(`orama network use`); switch back with `orama network use <previous>`.

**The sandbox and this test.** `orama maint sandbox create` (see [Sandbox](/docs/contributor/sandbox))
provisions servers and installs the cluster itself, over an SSH key, from its own
code path, so it cannot stand in for the page's install steps: those need machines
that are still bare and that have a password login. It does fit the second half.
`E2E_CLUSTER_MODE=use-only` skips the Install section (it is still matched against
the page) and runs Use it and Check it against a cluster that already exists:

```bash
orama maint sandbox create --name guide
E2E_CLUSTER_MODE=use-only E2E_CLUSTER_ENV=sandbox \
E2E_CLUSTER_BASE_DOMAIN=<the sandbox domain from orama maint sandbox setup> \
make e2e-cluster
orama maint sandbox destroy --name guide
```

`create` records the environment as `sandbox`. For the install half, use any
three fresh servers (a Hetzner project of your own, for instance), destroy them
afterwards, and expect about half an hour plus the DNS wait.

What it does not check: that the deployed site answers over HTTPS on its own
name (the page names no URL to fetch), and that the cluster survives a restart
(that is the lifecycle harness below).

## Fleet e2e (the release gate)

One command provisions a disposable three-node Orama fleet on Hetzner with a real Cloudflare delegation, real Let's Encrypt staging certificates and a throwaway RootWallet agent. It runs every feature package against it, stage by stage (eleven ordered stages from bootstrap through namespaces, auth, data plane, deployments, realtime, security audit, chain, ops and chaos and soak), collects artifacts, writes a report and always tears the fleet down.

```bash
make e2e-fleet E2E_RUNNER_CIDR=203.0.113.7/32        # the whole run (secrets through infisical)
make e2e-fleet E2E_FLAGS=--keep-on-fail
make e2e-coverage                                    # the coverage gate, no servers
make e2e-lint                                        # go vet with and without the tag, plus the contract lint
make e2e-test-unit                                   # the harness's own unit tests
```

`e2e-fleet target testnet --out state.json` followed by `E2E_FLEET_STATE=state.json e2e-fleet test --stage N` runs one stage against the existing testnet cluster instead of fresh servers; the runner only tests there and never provisions or destroys. The owner runs the fleet suite. As a contributor you write the feature package and run the gate, lint and unit targets. The full contract is `e2e/README.md`.

### Running the suite

`make e2e-fleet` runs `infisical run` against the `orama-e2e` project (environment `e2e`, folders `/hetzner`, `/cloudflare`, `/rootwallet`, `/release`, `/notify`), so the operator needs the Infisical CLI logged in, or a machine identity through `INFISICAL_CLIENT_ID` / `INFISICAL_CLIENT_SECRET`. The runner needs `HCLOUD_TOKEN`, `CF_API_TOKEN` and `CF_ZONE` (`dbrsteting.bid`), `E2E_RW_BIN` and `E2E_RW_AGENT_BIN` (the RootWallet CLI and the headless agent binary), plus `E2E_RUNNER_CIDR`, the public address of the machine running the suite (`a.b.c.d/32`): the run's Hetzner firewall lets only that address reach SSH (`E2E_ALLOW_OPEN_SSH=1` opens it to the internet instead). The Hetzner project behind `HCLOUD_TOKEN` must be used only for e2e: teardown and sweep delete by the `e2e-run` label. Nothing is persisted: the run works in a private directory, creates a throwaway RootWallet agent and wallet in an isolated home, delegates a per-run subdomain `e2e-<id>.dbrsteting.bid` through Cloudflare with Let's Encrypt **staging** certificates, and tears down the servers, DNS records, agent and secrets on exit (also on failure and on SIGINT/SIGTERM/SIGHUP).

| Command | What it does |
|---|---|
| `e2e-fleet test --stage N`, `--resume` | Re-run one stage, or continue an interrupted run |
| `e2e-fleet teardown`, `sweep` | Destroy a run's resources, or orphans by label (`sweep` removes anything a crashed run left behind) |
| `e2e-fleet sweep-namespaces [--max-age 4h] [--listed]` | Remove the test namespaces a run left on the cluster (also testnet): the runner already removes each package's recorded namespaces when the package exits; this takes what a dead runner left (`e2e/README.md`, "ns") |

Destructive packages run alone at the end of their stage. A skipped test counts as **not covered**, a re-run only labels a failure deterministic or flaky and never turns it green, and the exit code is 0 for PASS, 1 for FAIL and 3 for INCOMPLETE. The report (`report.html`, `report.json`, JUnit, optional Bugboard drafts) lands in the run's artifact directory next to the collected journals and node state.

### Signed reports, the push and the release gate

Two more secrets are optional, and a value that is set but unusable refuses the run before any server is created:

| Variable | Infisical folder | What it does |
|---|---|---|
| `E2E_RUNNER_SIGNING_KEY` | `/release` | The runner's Ed25519 private key, PKCS #8 PEM. Every report the run writes is signed: `report.attestation.json` beside `report.json` is a DSSE envelope over the run id, the commit (full SHA, `-dirty` when the tree had uncommitted changes), the verdict and the SHA-256 of `report.json`. Unset, the report is unsigned and no release can stand on it. |
| `NTFY_URL` | `/notify` | The ntfy topic URL, `https://push.<base domain>/<topic>`. When the run is over, after teardown, the final verdict is pushed once: the title names the verdict, the body is the `summary.txt` line, a FAIL is high priority. The Orama ntfy has no auth file, so the topic name is the credential; the URL is sealed and redacted like the cloud tokens. A push ntfy does not accept fails the run (exit 1). Unset, nothing is pushed. |

`e2e-fleet report` rewrites `report.json` from the artifacts and deletes the attestation: that report is not the one the runner signed.

**The release gate.** `core/scripts/release.sh` refuses to tag, and `orama maint release cut` refuses to sign a nightly or main release, unless the commit has a report that is signed by a key listed in `core/pkg/releasepub/runner-keys.txt` (compiled into the CLI), names exactly that commit with a clean tree, and has the verdict PASS: every feature green, and the coverage gate held, so anything uncovered is waived. An edited `report.json` no longer matches its signed digest. There is no override flag; changing who may vouch for a release is a reviewed commit to `runner-keys.txt`. To create the runner key and list it:

```bash
openssl genpkey -algorithm ed25519 -out runner.pem       # store the file's contents as E2E_RUNNER_SIGNING_KEY in Infisical /release
openssl pkey -in runner.pem -pubout -outform DER | tail -c 32 | base64   # the line for core/pkg/releasepub/runner-keys.txt
```

`release.sh` reads the run's artifact directory from `ORAMA_FLEET_REPORT`, or asks for it, and checks it with `go run ./tools/fleetgate -report <dir> -commit <sha>` from `core/`. A stable release tags the head of `main` after the merge, so a merge commit needs its own run.

### Chain chaos

`chain-chaos` is a destructive package of stage 11 that breaks one validator of the chain at a time, restores it at cleanup, and ends each test on a chain that moves on every validator with the same blocks and app hash on all of them:

| Test | What it does | What it asserts |
|---|---|---|
| `TestChainPartition_isolatedValidatorCatchesUpAfterHeal` | drops the validator's p2p TCP in both directions while public transfers keep arriving at a survivor | the others commit if and only if they hold more than 2/3 of the voting power (three equal seats halt, five commit); the isolated validator never gets ahead; after the heal it catches up and every transfer is delivered once |
| `TestChainKill_oramadKilledUnderLoadRestartsAndAgrees` | `kill -9` of the chain process under load | systemd restarts it, it replays to the head, it keeps its voting power |
| `TestShieldedVerifier_killedChildDoesNotMoveConsensus` | kills the shielded verifier child process while public transfers arrive | `oramad` keeps its process and the node stays on the same blocks |
| `TestChainDisk_fullVolumeHaltsWithALogLineAndRecovers` | fills the chain home's filesystem until no non-root user can write (root keeps 64 MiB); only where the chain home is a filesystem of its own, so the node's rqlite, ipfs, olric and gateway are never starved | the validator stops committing and its journal says `no space left on device`; it recovers when the space is freed |
| `TestChainClock_skewedValidatorDoesNotMoveBlockTime` | moves one clock two minutes ahead, then two behind | BFT time keeps block times at real time; an early clock shows in the validator's own precommit times, a late one is held at the block's time |
| `TestChainStateSync_wipedValidatorRestoresASnapshotAndAgrees` | wipes a validator's data (its sign state stays) and starts it | it restores a snapshot, reaches the head and agrees |

If the runner interrupts the package mid-fault, the sweep after every destructive package removes the run's tagged firewall rules (IPv4 and IPv6), restores NTP, and deletes the disk filler and the throwaway keyrings named for the run; a state-sync backup of a validator's old data (`data.e2e-<run>` in the chain home) is never deleted, the sweep fails and prints the steps to put it back.

Three tests apply only where the node was set up for them, and report not applicable (not covered) otherwise. The verifier test needs validators that run the verifier child process, which a run chain does not (`chain-deploy.sh` builds `oramad` without the Orchard library and ships no verifier binary). The disk test needs the chain home on a filesystem of its own, because filling the root filesystem would starve the node's rqlite, ipfs, olric and gateway too; a node that keeps the chain on the root filesystem skips it. The state-sync test needs a validator whose `config.toml` has `[statesync] enable = true`, which the installer writes only for a joiner, and other nodes that hold snapshots on disk; `chain-deploy.sh` configures neither, and the test never configures state sync itself. A shielded bundle being verified at the moment the child dies is not reached either: only the Rust wallet builds a bundle with a valid proof, so the halt on a verifier fault in a block (`checkInBlock` stops the node and records no result) is proven by the keeper's unit tests and by `chain/app`'s test with a verifier that dies, and the fleet test only shows that the node stays on the same blocks as its peers.

### Chain soak

`chain-soak` is a destructive package of stage 11 that is **opt-in**: the runner plans, budgets and reports it only when its environment sets `E2E_CHAIN_SOAK` to a Go duration (`E2E_CHAIN_SOAK=24h`, between ten minutes and a week; 24 to 72 hours for the owner's run). A plain `make e2e-fleet` does not run it and its verdict does not change; with the variable set the package gets the stage's timeout plus the duration, the fleet's e2e-ttl grows by the same, and a failure is not re-run. It drives steady load on the run's chain, samples every validator every five minutes and fails on a divergence, a halt or memory that only grows. [Performance](/docs/contributor/performance#the-chain-soak) lists what it samples and its thresholds.

### The coverage gate

`make test` runs `make e2e-coverage`. It fails on any CLI command, gateway route, chain message or query, or systemd unit that no feature package claims under `covers:` in its `feature.yaml`, and on any entry that matches nothing that ships (a typo cannot cover anything). What has no test yet needs a waiver in `e2e/waivers.yaml` with a reason and a trigger.

### Writing a feature package

1. `mkdir e2e/features/<id>` (lowercase letters, digits, hyphens; equals the manifest `id`).
2. Write `feature.yaml` (`id`, `title`, `area`, `stage`, `destructive`, `requires`, and `covers` with `cli`, `routes`, `msgs`, `queries`, `units`, `config`, `claims`), `main_test.go` (a `TestMain` calling `harness.Main(m)`), and tests. Every `.go` file starts with `//go:build e2e_fleet`.
3. `make e2e-lint && make e2e-coverage`, then `go vet -tags e2e_fleet ./features/<id>/`.

The rules the lint enforces:

- **No sleeps.** `time.Sleep`, `After`, `NewTimer`, `Tick`, `NewTicker` and `AfterFunc` are banned. Wait for a readiness signal with `eventually.Require`, `Eventually` or `Poll`.
- **No bare skips.** `t.Skip` is banned; use `harness.SkipNotApplicable(t, reason)`. Every skip counts as "not covered".
- **Clean up everything**, with a cleanup that restores and verifies. Cleanups get their own context (`fleet.CleanupContext(t)`), because `t.Context()` is cancelled before cleanups run.
- **One namespace per test** (`ns.New`), never a shared one. A namespace lives on three nodes, so a per-namespace check loops over `tenancy.Members(t, f, name)`.
- **Real paths only.** Requests go to the public name through DNS and TLS pinned to the run's CA. Logins are real signatures. Operator actions go through the CLI under test. SSH observes nodes and injects failures, never sets up state the product should set up.
- **No retries that turn red into green.** The runner re-runs a failed test once, alone, only to label it deterministic or flaky.
- **Destructive tests** (kill, partition, reboot, upgrade) go in a `destructive: true` package, usually stage 9 to 11.
- **Credential calls are paced** by the harness under the gateway's rate limits (30 a minute, burst 10 per address; challenges 10 a minute, burst 5 per wallet). A 429 on a paced request is a `PacingError`, never retried.

Test names are `Test{Function}_{scenario}`.

## Chain simulation

`make -C chain chain-sim` runs a seeded, randomized simulation of the chain (`chain/app/sim_test.go`): a real app driven through `InitChain` and `FinalizeBlock` with random valid and invalid transactions across x/bank, x/staking, the faucet and x/token. After every block it runs the full conservation pass and compares x/token's balances, issued supplies and flags with a model written from the documented rules. It fails with the seed, so `make -C chain chain-sim SIM_SEEDS=42 SIM_BLOCKS=500` reproduces a failure. For each seed it also runs, under the race detector, the determinism test (two apps fed the same genesis and blocks must agree on the app hash, every result and every event at every height) and the export/import round trip. `SIM_SEEDS` defaults to five seeds and `SIM_BLOCKS` to 200. The chain halts itself on a conservation violation, so a violation fails the run at the block that caused it.

The chain runs its own full pass every `min_blocks_per_epoch` blocks, so each seed runs once per cadence in `SIM_CADENCES` (default `1 7`): at 7 the chain looks at some heights only, and the simulation's own pass still looks at every block. Flows the random run does not reach have tests of their own (`app/conservation_flows_test.go`, `app/conservation_contracts_test.go`), each run at both cadences with the pass after every block: unbonding delegations queued and matured, a slash that burns from the bonded pool and from an unbonding entry, a storage deal's escrow from creation to payout, and contracts holding norama and a factory token. `make chain-sim` ends with one run at the production setting, 14,400, to the first height where a production chain runs the pass itself (`-sim.production-cadence`).

## Lifecycle harness

`make test` and `make test-e2e` never reboot a node, kill a voter, join one, or
upgrade one — `e2e/cluster` tests read-consistency levels and `e2e/production`
stops a deployment process. That is why the change-287 stability audit's
findings all had to be established by reading code: nothing could observe them.

`e2e/lifecycle` closes that gap. It drives a real 3-node cluster **only through
the `orama` CLI** and observes it **only through `orama status report --json`
and `dig`** — a harness that reaches around the CLI would test a path no
operator runs, and could pass while the CLI reported something different.

```bash
ORAMA_LIFECYCLE_ENV=<disposable-env> make -C core test-lifecycle
```

`orama status report` reads the gateway's operator telemetry API, so the
machine running the harness needs an operator session for that environment
(`orama network use <env>`, then `orama auth login`). The reports it returns are a
few seconds old (the gateway gathers each node's telemetry every 10s and caches
a snapshot for 5s); `Converged` refuses a node whose report is older than 30s.

**Never point it at testnet or mainnet.** These scenarios reboot nodes and
destroy VMs; the harness refuses those two names outright.

| Scenario | What it proves |
|----------|----------------|
| Reboot one node | Quorum holds; the node comes back with a complete mesh and no crash-loop |
| Reboot all three | DNS and the gateway answer within 90s **before** raft has a leader, then the cluster converges |
| Kill a voter (VM destroyed) | Survivors keep committing; every membership view — raft *and* WireGuard — forgets it |
| Join a fourth node | It becomes a full member of every store, not just raft |
| Decommission a node | Same end state as an abrupt death, reached cleanly |
| Rolling upgrade, one node broken | The rollout **stops**, names the node, and leaves the leader untouched |
| Rolling upgrade, healthy | The leader is the last step in the plan |
| Index rqlite down everywhere | DNS still answers, from the stale cache |

Four things have no CLI equivalent, because they are not things the CLI should
be able to do: destroying a VM abruptly, breaking a node so an upgrade fails on
it, creating a new VM, and (for DNS) naming the zone. Each is a command you
supply — Multipass, Lima, a cloud CLI:

| Variable | Purpose |
|----------|---------|
| `ORAMA_LIFECYCLE_ENV` | The disposable environment (required) |
| `ORAMA_LIFECYCLE_DESTROY` | Destroy a node abruptly; receives the host as `$1` |
| `ORAMA_LIFECYCLE_BREAK` | Make an upgrade fail on a node; receives the host as `$1` |
| `ORAMA_LIFECYCLE_PROVISION` | Create a node; prints its IP on stdout |
| `ORAMA_LIFECYCLE_BASE_DOMAIN` | The zone the DNS scenarios query |
| `ORAMA_LIFECYCLE_RESOLVER` | Resolver for `dig` (defaults to the system resolver) |
| `ORAMA_BIN` | The binary under test (defaults to `./bin/orama`) |

A scenario whose hook is not set **skips** rather than passing — a green run
that silently omitted the kill-a-voter scenario would be worse than no harness.

The convergence predicates (`Converged`, `LeaderAgreement`, `Forgotten`,
`Serving`) are plain Go with no build tag, so `make test` exercises them against
recorded report shapes. That is what stops the harness from going green by
asserting nothing.

## Older end-to-end suites

`core/e2e` predates the fleet suite and runs against an environment that already exists (a sandbox or a real cluster; the gateway comes from `ORAMA_GATEWAY_URL`, else the active environment). The targets are in `core/Makefile`: `make test-e2e` (all), `test-e2e-quick` (smoke), `test-e2e-deployments`, `test-e2e-fullstack`, `test-e2e-https`, `test-e2e-shared`, `test-e2e-cluster`, `test-e2e-integration` and `test-e2e-production`. None of them is part of an automatic gate; run the ones that match before merging a change that touches deployment, clustering or cross-node behaviour. ## CI

Every third-party action in `.gitea/workflows` and `.github/workflows` is pinned by its full commit SHA with the release as a `# vX.Y.Z` comment, so a moved tag cannot change what CI runs; `.github/dependabot.yml` opens the weekly pull request that moves a pin. The nightly Rust toolchain of the Miri and AddressSanitizer jobs is a dated build too (`RUST_NIGHTLY` in `chain/ci.mk`).

`.gitea/workflows/ci.yml` runs on a release tag (`v*`), on pull requests to `main` and `nightly`, and on demand (`workflow_dispatch`); a plain branch push runs nothing. Its jobs: the core module (vet, then every test under the race detector with `-count=1`, which includes the contract tests and the generated CLI reference), the OramaOS agent, the SDK, the Vault SDK, the Vault guardian (Zig), the chain, and a secret scan. `security.yml` runs `pnpm audit` on the SDK and `govulncheck` on `core` (with accepted advisories listed in `e2e/features/scanners/govulncheck-accepted.yaml`, each with a reason and a review date) for `main`, and on Mondays; `release.yml`, on a `v*` tag, checks that the `VERSION` file matches the tag, builds the binaries and `.deb` packages with GoReleaser and publishes the packages to the Gitea Debian registry, builds the cluster archive twice and fails unless the two are identical (the amd64 job first checks that `chain/native/build.sh verify` reproduces the recorded native library hash), and publishes both SDK packages to the Gitea npm registry.

**Caches.** The runners are self-hosted (act_runner, label `orama`, a fresh container per job). Each job restores its own Go module and build cache and, if it builds Rust, its own cargo registry and target directories, through act_runner's cache server (`actions/cache`), keyed on the job, the toolchain and the lock files of what it builds. setup-go's own cache is off: it keys on `go.sum` alone, so every job of a module shared one entry, written by whichever job finished first, and the others compiled from cold. act_runner evaluates `hashFiles()` on the runner host, where the checkout is not, and gets an empty string, so `.gitea/scripts/cache-key.sh` hashes the lock files inside the job instead. An entry is written once, by the first passing run that misses its key, and each runner host has its own cache server. Because the build cache also holds test results, the Go test steps run with `-count=1`: every test runs on every run. `cargo-audit` and `cargo-deny` are installed from their upstream release archives, checked against the sha256 pins in `chain/ci.mk` (`chain/scripts/release-tool.sh`), not compiled.

### The chain in CI

Every command the chain jobs run is a target of `chain/Makefile` or `chain/ci.mk`, so a developer runs the same thing with `make -C chain <target>`. Tool versions are pinned in `chain/ci.mk` and nowhere else.

| Job | What it runs | Target |
|---|---|---|
| `chain-test` | the release cross-builds; `go vet` under each build-tag set (none, `nowasm`, `nowasm orchardffi`); the pure-Go tests (`-tags nowasm`); then every package under the race detector with CosmWasm, the Orchard verifier library (cgo) and the out-of-process verifier binary all linked, so the cgo and subprocess tests run and do not skip | `build`, `vet-all`, `test`, `test-race` |
| `chain-static` | staticcheck, gosec (high severity, high confidence) and govulncheck under two build-tag sets that together cover every file (the default build, and `nowasm orchardffi`); the consensus-determinism rules (semgrep) over the state machine, and the tests of those rules | `staticcheck`, `gosec`, `govulncheck`, `semgrep`, `semgrep-test` |
| `chain-rust` | `cargo clippy --all-targets -D warnings`, `cargo audit` and `cargo deny` (policy in `chain/deny.toml`) over `orchardffi`, `orchardverifier-bin`, `wallet`, `native` and, for audit and deny, the test contracts; then the check of the ignored advisories | `rust-lint`, `rust-audit`, `rust-deny`, `rust-ignores` |
| `secrets` | gitleaks over the committed tree, with the allowlist `.gitleaks.toml` (a public fixture that trips a rule is allowed by its path and its exact value together, so a real credential added to the same file is still found) | none |

`make test` runs the pure-Go tests of `chain`, and, when `make -C chain orchard-lib orchard-verifier` has built the Orchard library and the verifier binary on the machine, the `orchardffi` tests of `x/shielded`, `app` and `indexer` too (the real proofs through `FinalizeBlock`, the real note-commitment tree); without them it says it skipped those. They always run in `chain-test`, so a stale expectation in one is caught there at the latest, but the pull-request job is late for it: build the library once and `make test` catches it before the push.

`make -C chain ci` runs the first three jobs' commands in one go; it builds libwasmvm and the Orchard verifiers first, so it takes a while.

`test-race` builds libwasmvm from the source in the Go module cache (`wasmvm-lib`: the version `go.mod` pins, checked against `go.sum`) and links it with `-tags sys_wasmvm`. It builds against `chain/native/Cargo.lock` with the `cosmwasm-crypto` fork patched in, as the release library does, so the tests run the crates that ship; cargo builds it into `build/wasmvm-target`, which survives the fresh copy of the source each run makes, so its dependencies compile once. Nothing prebuilt is downloaded, the same rule `native/build.sh` follows for the release library. On Linux the copy is given the release library's `__rust_probestack` (`native/src/probestack.rs`), without which no test binary links with the pinned Rust toolchain.

staticcheck and govulncheck are judged the way the fleet `scanners` feature judges them, by `e2e/cmd/scangate`, which reuses the fleet code (`harness/vulnaccept`, `harness/staticfind`) without a fleet. A reachable vulnerability that is not in `e2e/features/scanners/govulncheck-accepted.yaml` fails, and so does an entry that govulncheck no longer reports and one past its `review_by`. The only staticcheck findings tolerated are the deprecation warnings in files protoc-gen-grpc-gateway v1 generated. A scanner that crashed, or printed nothing it could parse, is a failure and never a clean run.

**The consensus rules.** `chain/.semgrep/consensus.yml` flags, in `app/`, `x/*/keeper`, `x/*/types`, `x/*/ante` and `x/inclusion`, everything that can make two validators compute different state from the same block: ranging over a map, `time.Now` and its relatives, floating point, goroutines, and the `math/rand`, `math/rand/v2` and `crypto/rand` packages. A finding is fixed or suppressed on its own line with `// nosemgrep: <rule-id> -- <reason>`, and the reason says why the order or value cannot reach the app hash (the keys are sorted next; the result is a set; the sum is of exact integers). `chain/.semgrep/consensus.go` holds the rules' own test cases (`make -C chain semgrep-test`). The map rule relies on semgrep's type inference, which resolves a map only when its type is visible in the same function or file, so it is a net and not a proof: new state-machine code that ranges over a map is still reviewed for order by a person.

**The Rust crates.** The crates are checked with the toolchain `native/build.sh` builds with. clippy runs over every target, examples included, and one lint is switched off for a stated reason (`CLIPPY_ALLOW` in `chain/ci.mk`). `chain/deny.toml` allows crates.io only, no source repositories, permissive licences (MPL-2.0 for three named crates), and lists each ignored RustSec advisory with its reason. The ignored advisories are all in `chain/native/Cargo.lock`, which is seeded from libwasmvm's own lock file; changing it changes the hash-pinned static library, so those updates are taken with the next wasmvm bump. A vulnerability with no such reason is fixed in the lock instead: `cosmwasm-crypto` is patched in from `chain/native/patches/cosmwasm-crypto` (on the RustCrypto 0.14 curve crates, for RUSTSEC-2026-0387), and `make -C chain native-crypto-test` (in the `chain-rust` job) runs upstream's ECDSA suites on the fork and a differential test against the crates.io release. The test contracts under `app/testdata` are checked by `cargo deny` alone, on `wasm32-unknown-unknown`: each is only ever built for that target into its committed `.wasm`, and cosmwasm-std's host-only dependencies (cosmwasm-crypto and its curve crates) are not in that graph, while `cargo audit` reads every package of a lock file whatever the target. `cargo audit` ignores the same ids (`RUST_AUDIT_IGNORE`); change both lists together. `make -C chain rust-ignores` (`chain/scripts/rustignores`) keeps the ignores honest: every reason carries a `review-by YYYY-MM-DD` and the build fails on the day after it, the two lists must name the same ids, and an ignored id that `cargo deny` finds in none of the crates' lockfiles (it reports `advisory-not-detected` in every crate) fails too, so the ignore is removed.

### Nightly

`.gitea/workflows/chain-nightly.yml` runs the checks that are too slow or too noisy for a pull request. It has no effect on a merge, and a red run is a finding to read.

| Job | What it runs | Target |
|---|---|---|
| `mutation` | mutation testing (gremlins) of the money modules, one job per package: `x/emission`, `x/fees`, `x/power` and the settlement code of `x/storage`. A surviving mutant is a change to the code that no test notices. Fails below `MUTATION_EFFICACY` percent in a package | `mutation` |
| `nilaway` | nil-flow analysis of the non-test code. It reports nils that a caller could pass without knowing the invariants that rule them out, so the report is read by a person | `nilaway` |
| `rust-sanitizers` | Miri over the `orchardffi` unsafe surface (both `extern "C"` entry points with bad arguments, and the framing refusals of `verify`), and the whole crate test suite, real proof vectors included, under AddressSanitizer | `rust-miri`, `rust-asan` |

Miri does not run the proof and Merkle-hashing tests: halo2 and Sinsemilla take hours under an interpreter. Its Stacked Borrows check flags `bitvec` 1.1.1, inside the upstream `sinsemilla` crate, as soon as a frontier is hashed; that is upstream's finding and outside what the job runs.

### Fuzzing

There are 54 Go fuzz targets (`func FuzzX(f *testing.F)`) and 5 cargo-fuzz targets. Each takes the bytes or the inputs of one parser, decoder or verifier that handles data it does not trust, and checks a property that is more than "does not crash": a round trip, `verify(prove(x))`, refusal after a mutation, agreement between two implementations, determinism, or a model of what the code must do. `go test` replays every seed of a target as an ordinary test, so a seed that fails is a failing test.

`make -C chain fuzz-list` prints the targets. `make -C chain fuzz-short` runs each Go target for `FUZZ_TIME_SHORT` (10 seconds), two targets at a time with two workers each, in `chain` (tags `nowasm orchardffi`, so the cgo and subprocess targets run) and in `core`. `make -C chain fuzz-long` does the same for `FUZZ_TIME_LONG` (5 minutes; `fuzz-long-chain` and `fuzz-long-core` run one module). `FUZZ_ONLY='netclass|piece'` picks targets by `package/FuzzName`. The runner is `chain/scripts/fuzzrun`: it finds the targets, runs them, prints one line per target (package, target, executions, time, verdict) and exits non-zero when one failed. A failing target leaves its input in the package's `testdata/fuzz/<Target>/`, where `go test` replays it from then on, and a copy under `chain/build/fuzz-crashers/` (CI uploads that directory). Commit the input with the fix.

| Where | What it runs | Budget |
|---|---|---|
| `ci.yml`, job `chain-fuzz` (every pull request) | `fuzz-short`: all 54 Go targets | 10 seconds each plus start-up; job timeout 45 minutes |
| `chain-nightly.yml`, job `fuzz-go` (nightly, one job per module) | `fuzz-long-chain` and `fuzz-long-core` | 5 minutes each: about 100 minutes for the 40 targets of `chain` and 35 for the 14 of `core` (counted from the budget, two targets at a time; job timeout 240 minutes) |
| `chain-nightly.yml`, job `fuzz-rust` (nightly) | `rust-fuzz`: the five cargo-fuzz targets, 600 seconds each, on the dated nightly Rust of `RUST_NIGHTLY` | about 40 minutes plus the build |
| The fleet `scanners` feature (owner runs it) | the `core` targets, 20 seconds each | |

**Why 10 seconds.** A target pays its start-up before it fuzzes: the app targets build a whole chain in each worker, and the Orchard targets link the Rust library. Measured on a laptop with other jobs running (load average above 16), `fuzz-short` took 7 minutes 17 seconds for the 39 targets of `chain` known then, 1 minute 29 seconds for the 14 of `core`, and 4 minutes of Rust builds before them; a target took 11 to 20 seconds from start to verdict, and the app targets 44 to 124 seconds because of their start-up. Ten seconds is enough to replay every seed and to mutate them for tens of thousands of executions for the cheap targets (one million for `x/inclusion`, 300,000 for `netclass`) and for a few hundred for the heavy ones. The job runs on a four-core runner with two targets at a time and two workers each, and its timeout is 45 minutes. A longer budget belongs to the nightly run, which finds what ten seconds do not.

**Seeds.** Every target starts from real data where the repository has it. The Ironwood bundles of `chain/x/shielded/orchardffi/testdata`, the signed transactions of `chain/client/tx/testdata/tx_vectors.json`, the piece vectors, the testnet network manifest and Tor network file, and a Tor vote are committed as corpus entries in each target's `testdata/fuzz/<Target>/` (`make -C chain fuzz-corpus` rebuilds them with `chain/scripts/fuzzcorpus`). The other targets seed themselves with `f.Add` from objects their package builds (a TUF repository from fixed keys, a bundle from real blocks, a committee chain with a listed transaction). The cargo-fuzz seeds are in each crate's `fuzz/seeds/<target>/`; the corpus the fuzzer grows is ignored by git.

**The cargo-fuzz targets** (`chain/x/shielded/orchardffi/fuzz`, `chain/x/shielded/orchardverifier-bin/fuzz`): `ffi_verify` sends arbitrary bytes through `orama_orchard_verify`, the entry oramad calls, and treats a caught panic as a failure; `tree_append` sends arbitrary frontiers and commitments through `orama_orchard_tree_append` and checks the output capacity and the two-step rule; `wire_read` compares the library's bundle reader (`src/wire.rs`) with `zcash_primitives` 0.30.1 `read_v6_bundle`, the reader it replaced, and requires the same refusals and the same bundle; `stdin_frames` drives the verifier process's whole frame loop (`protocol::serve`) with arbitrary stdin and checks that every request that was read whole gets one well-formed answer with its id; `check_framing` compares the framing check of the out-of-process verifier with the library's on the same bytes, because two nodes with different verifiers must refuse the same bundles. The fuzz crates have their own `Cargo.lock`, seeded from the crate's pinned one, and are not built into oramad.

**What the targets found.** Writing them found four defects, all fixed with a test that fails without the fix: a transaction whose auth info states no fee, or a fee coin with no amount, crashed `VerifyVoteExtension`, which makes CometBFT halt the node (`chain/app/inclusion_nofee_test.go`; the second form is one the fuzzer's random bytes cannot build, a review found it); a state-sync stream could store a record at a negative height (`chain/x/shielded/snapshot/snapshot_test.go:TestRestore_refusesARecordAtANegativeHeight`); the gateway's refusal log let invalid UTF-8 hide an address from the redaction patterns (`core/pkg/gateway/handlers/chainread/sanitize_utf8_test.go`); and `clusterreg.Validate` accepted endpoint hosts that the chain refuses (`core/pkg/clusterreg/validate_hosts_test.go`). The client's `Builder.Decode` had the same missing-fee panic as the first. One finding is left alone on purpose: a transaction with no fee panics in the first decorator of the ante chain, which BaseApp recovers per transaction with the panic code, the same on every node; refusing it earlier would change that transaction's result code in a block, a consensus change, so `FuzzCheckTx` tolerates the panic for transactions that state no fee and for no others.

### Simulation

`make -C chain chain-sim` runs the seeded, randomized simulation described above. CI does not run it on every push; run it before a change to a module's state machine.

### The pre-push hook

`core/.githooks/pre-push` runs `go test ./...` in `core`, then builds the chain (`-tags nowasm`) and vets it under the default and `nowasm` build-tag sets (`make -C chain vet-all` runs all three, and CI does). The race-detector tests stay in CI so the hook stays short. The hook removes the `GIT_*` variables git sets for hooks before it runs anything: a test that calls git and inherits them acts on the repository being pushed.

### What CI does not run

The fleet suite (`make e2e-fleet`) is run by the owner. Of the `scanners` feature, CI covers `govulncheck`, `staticcheck`, `gosec` and the secret scan for the chain module only (`core` has `security.yml`; the other modules, the scan of the built archive and the race run over the busiest core packages are fleet-only). The fuzz targets of `core` run there too, 20 seconds each, as the fleet's fuzz smoke.
