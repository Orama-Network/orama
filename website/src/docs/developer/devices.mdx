# Devices

A session used to belong to an account and nothing else. Every installation of an application signed in as the same wallet held interchangeable sessions, so losing one phone meant ending every session the account had, and nothing a function ran could tell which installation was calling.

A session may now be bound to a **device**: a key pair one installation holds.

## What a device is

- The gateway accepts **ECDSA P-256** (ES256, what iOS's Secure Enclave, Android's StrongBox and WebCrypto keep non-extractable) and **Ed25519**.
- The device's id is the RFC 7638 thumbprint of its public key. It is computed, never stated, so a client can name only a device whose key it presents.
- A signature is base64url; a P-256 one may be the 64-byte `r || s` JOSE form or ASN.1 DER.
- A key belongs to one account in one namespace. The lobby binds none. A revoked device is a tombstone: its key can never sign in again, by anyone. An Ed25519 key of small order, which "verifies" signatures nobody made, is refused.

A session bound to a device:

- is issued only against the device's signature over the same sign-in message the wallet signed;
- is refreshed only with a fresh proof from the device;
- carries the device in its access tokens as `did`, which a function reads with `get_caller_device_id` the way it reads the account with `get_caller_jwt_subject` (and by which it admits, kicks or checks that one device in a WebRTC room: [Admitting one device](/docs/developer/webrtc#admitting-one-device));
- ends, with its refresh tokens, access tokens and every socket they hold open, when the device is revoked, while the account's other devices stay signed in.

Binding a device is the client's choice in every namespace. A namespace's session policy decides what a sign-in that binds none may still get. Sessions without a device keep working as before.

## Signing in with a device

```text
client                                          gateway
  | POST /v1/auth/challenge                       |
  | { wallet, namespace, device_id }  ----------->|  message's Resources carry urn:orama:device:<id>
  | <-- message naming the device -----------------|
  | the wallet signs the message                  |
  | the device key signs the same message         |
  | POST /v1/auth/verify                          |
  | { message, signature, device_key,             |
  |   device_signature, device_label } ---------->|  both signatures, one spent nonce
  | <-- access + refresh token, device_id --------|
```

`orama auth login --device-key <file>` does this. The file is an Ed25519 private JWK (RFC 8037: `d` is the 32-byte seed, base64url, and `x` must be its public key) and stays on the machine that signs in. The request carries the public half. In the SDK see [Device-bound sessions](/docs/developer/sdk-reference#device-bound-sessions).

A device-bound sign-in is **not handed an API key**: the device is the credential, and a key for the whole account beside it would outlive revoking the device.

The access token of a device-bound session is still a bearer token for its 15 minutes. The device's proof guards what outlives it: the refresh, and the acts listed below. A device-bound refresh token is marked `dv1_` and stored under a hash of its own, so a gateway that predates devices cannot find it, and so cannot refresh it without the device.

## Proving the device on later requests

Refreshing a device-bound session, approving a link from a device, collecting a linked session, and (from a device-bound session) revoking a device, ending a session or logging out everywhere each carry a **device proof**:

```json
"device_proof": { "iat": 1790000000, "id": "<16-128 chars of [A-Za-z0-9_-], random>", "sig": "<base64url>" }
```

`sig` is the device's signature over this text, lines joined by `\n`:

```text
orama-device-proof-v1
<action>          refresh | approve | claim | revoke | end-session | logout-all
<namespace>
<binding>         the refresh token | the user code | the device code | the device id | the session id | the caller's own device id
<iat>
<id>
```

`iat` must be within 60 seconds of the gateway's clock, and `id` is spent in the nonce table, so a proof is good once, for one action on one credential. A phone's clock can be minutes off (set by hand, a dead clock battery, a network serving the wrong time), so stamp `iat` on the gateway's clock: every answer's `Date` header is that clock, and a proof refused for its time answers `DEVICE_PROOF_CLOCK_SKEW` with `server_time` (unix seconds). Nothing is spent by that refusal; sign a new proof, with a new id, on `server_time`. The SDK does both on its own. A refusal for time is the phone's clock, never a forged or replayed proof: tell the user their clock is wrong rather than signing them out. In a namespace that attests devices, an iOS app's refresh proof also carries `app_attest`, an App Attest assertion over `SHA-256(id ‖ device_id)` ([Device attestation](/docs/developer/device-attestation)). A refresh without the proof is refused before anything is spent, so a thief holding only the refresh token cannot use it up.

## Revoking a device

```text
GET    /v1/auth/devices          the account's devices, revoked ones included
DELETE /v1/auth/devices/{id}     revoke one
```

Revoking tombstones the device, revokes its refresh tokens (including the reuse-grace slot a just-rotated one would still have) and puts `device:<id>` on the revocation list, so its access tokens and sockets stop within ten seconds on every gateway. The account's other devices are untouched. Push registrations made from the device end with it.

Any of the account's sessions may revoke any of its devices: one bound to an active device, with that device's proof, or, under the `optional` policy, one bound to no device (which only the wallet can have made). The proof is what stops an access token lifted off one phone signing the account out of all the others. Under any other policy a session bound to no device is refused here with `DEVICE_REQUIRED`: none is issued there, and one minted before the policy was set does not get to revoke the devices the policy now protects. A session bound to a pending or revoked device can do nothing here.

Logging out everywhere is held to the same rule. `POST /v1/auth/logout` with `"all": true` ends every session of the account, its refresh tokens and the access tokens already issued. From a session bound to a device it carries that device's `logout-all` proof over the device's own id, or it is refused `DEVICE_PROOF_REQUIRED` and every session stays valid. A session bound to no device needs none under `optional`; under any other policy it is refused `DEVICE_REQUIRED`, as on the devices and sessions routes.

**When the user cannot help themselves.** Under the `approval` policy an account that lost its only device has nothing left that can approve a new one, and a wallet signature alone cannot, by design. A namespace operator (members-write permission) can:

```text
GET    /v1/namespace/devices?subject=<wallet>   an account's devices
DELETE /v1/namespace/devices/{id}               revoke one of them
```

With no active device left, the user's next sign-in enrols its device as the account's first again.

### What a revoked device is told

An application may erase a device that is told `DEVICE_REVOKED`: its data, session and keys. So that a misbehaving gateway cannot erase a healthy device by saying so, every `DEVICE_REVOKED` answer carries `revocation`, which the client checks with keys it already trusts before it acts:

```json
{
  "code": "DEVICE_REVOKED",
  "revocation": {
    "device_id": "<the revoked device: compare it with your own id>",
    "revoked_at": "2026-10-28T10:00:00Z",
    "revoked_by": "device",
    "proof": {
      "namespace": "anchat",
      "device_id": "<the revoking device>",
      "public_key": { "kty": "OKP", "crv": "Ed25519", "x": "..." },
      "iat": 1793181600,
      "id": "...",
      "sig": "..."
    },
    "evidence": "<what the revoker attached, verbatim, or null>"
  }
}
```

`revoked_by` is `device` (another of the account's devices, or the device itself, with its revoke proof), `account` (a session bound to no device: the wallet's own, under `optional`), `operator` (`/v1/namespace/devices`), `function` (`deny_device`), or `unrecorded` (revoked before the gateway kept this). Only `device` comes with a `proof`; the others are the gateway's word, with `proof: null`.

To check a proof:

1. `revocation.device_id` is this device's id.
2. `proof.namespace` is this device's namespace.
3. `proof.device_id` is the RFC 7638 thumbprint of `proof.public_key`.
4. `proof.sig` verifies under `proof.public_key` over the device-proof statement for `revoke` whose binding is the revoked device's id: `orama-device-proof-v1`, `revoke`, `proof.namespace`, `revocation.device_id`, `proof.iat`, `proof.id`, joined by newlines.
5. `proof.device_id` is a device you trust: this device itself, or one your application knows to be the account's. Do not skip this: anyone, a gateway included, can make a key and sign that statement with it.

The proof cannot be shown to another device (it names the revoked one) or carried to another namespace. `iat` is not checked against the clock: a revocation is permanent. The TypeScript SDK does all five: `verifyDeviceRevocation(deviceRevocationOf(err), { deviceId, namespace, trustedDeviceIds })` answers `proven`, `unproven` (`no_proof`, or `untrusted_revoker`) or `invalid`. Act at once on `proven`; on `unproven`, check `evidence` or your own records; treat `invalid` as a gateway that is misbehaving.

**Evidence.** The revoker may attach the application's own proof, such as an account-signed roster entry: `"evidence"` beside `device_proof` on `DELETE /v1/auth/devices/{id}` (`client.auth.revokeDevice(id, { evidence })`), or alone on `DELETE /v1/namespace/devices/{id}`. It is at most 16 KiB of UTF-8 (base64 is a good fit); the gateway stores it with the tombstone and returns it verbatim, and never reads it. Whatever it must bind, the account and the revoked device included, is for your application to put in it and check. A device's tombstone keeps the first revocation's record: revoking it again changes nothing in it. `deny_device` attaches none.

`DEVICE_REVOKED` is only ever about the device presenting itself. Collecting a device link whose approving device has since been revoked answers `access_denied`. A revoked device's access tokens and sockets are refused with `AUTH_REVOKED` and close code 4403, and its refresh token was revoked with it (`401`); the answer that carries `revocation` is its next sign-in.

## Device policy

`orama namespace session-policy --device-policy <policy>` (or `PUT /v1/namespace/session-policy {"device_policy": …}`; needs namespace write) sets what a sign-in must prove.

| Policy | A sign-in that binds no device | A new device's first sign-in |
|---|---|---|
| `optional` (default) | A session bound to the account | Active |
| `required` | Refused, `DEVICE_REQUIRED` | Active |
| `approval` | Refused, `DEVICE_REQUIRED` | Active if it is the account's first; otherwise **pending** |
| `function` | Refused, `DEVICE_REQUIRED` | Active if it is the account's first ever; otherwise **pending**, with a restricted session the namespace's functions decide on ([below](#devices-admitted-by-a-function)) |

Under `required`, `approval` and `function`, nothing else hands an end user a credential bound to no device either: `POST /v1/auth/api-key` and approving a plain `orama auth login` device code answer `DEVICE_REQUIRED`, and so does refreshing an end user's session bound to no device, so turning the policy on ends those sessions at their next refresh, within fifteen minutes. Setting any policy but `optional` also **revokes every key an end user's sign-in minted** in the namespace, and the response says how many (`revoked_sign_in_keys`). If the sweep stops partway the policy is still set and audited and the answer is `503 POLICY_SWEEP_INCOMPLETE`; repeating the `PUT` finishes it.

A wallet holding a control-plane role in the namespace (owner, admin, developer) is held to `optional` whatever the policy says. The policy protects the application's users; the people operating the namespace sign in from the CLI, which holds no device key, and whoever holds such a wallet can change the policy anyway.

## Adding a device: approval and linking

A **pending** device holds no session. The sign-in that enrolled it answers `202` with `status: pending_approval`, a `user_code` and a `device_code`: the new device shows the user code, one of the account's active devices approves it, and the new device collects its session.

```text
new device                         gateway                   an active device
  | (sign-in -> 202, or:)            |                              |
  | POST /v1/auth/device             |                              |
  | { namespace, device_key } ------>|  a pending login holding     |
  | <-- device_code + user_code -----|  the new device's key        |
  |                                  |  POST /v1/auth/devices/approve
  |                                  |  { user_code, device_proof } |
  |                                  |<-----------------------------|
  | POST /v1/auth/device/token       |                              |
  | { device_code, device_proof } -->|                              |
  | <-- access + refresh, device_id -|                              |
```

Starting the link from the new device (`POST /v1/auth/device` with `device_key`) is **seedless linking**: no wallet is involved at all, and the new device takes its account from the device that approves it. Starting it from an approval-policy sign-in is **new-device approval**: the wallet already named the account, and only one of that account's devices may approve. Either way the approver proves it holds its own key over the user code, and collecting the session takes the new device's proof over the device code. The codes alone collect nothing, and the approving device must still be active when the new one collects: revoking a stolen approver reaches the device it let in, whose collection then answers `access_denied`. A device link cannot be approved with a wallet signature (`orama auth approve`), and a plain login cannot be approved by a device.

## Devices admitted by a function

The `function` policy is for an application that runs its own admission: a new phone sends a join request that an existing phone answers, and both show a code to compare; or an account that lost every device passes the application's recovery check. The new device needs a session while that runs, and the gateway needs to keep it at arm's length until the application says yes.

Under `function`, the account's first device ever signs in active, as under `required`. Every later one signs in at once (`200`, not `202`) to a **restricted session**: the sign-in answer carries `device_state: "pending"` beside `device_id`, and its access tokens are minted for the audience `gateway-pending-device`. "First ever" counts revoked devices too, so an account whose devices were all revoked is recovering, and its next device is pending like any other: a stolen seed phrase gets no further once the owner's last device is gone.

A restricted session reaches:

- its own session: `POST /v1/auth/refresh`, `POST /v1/auth/logout` (its own session only; `all: true` is refused), `GET /v1/auth/whoami` (which reports `device_state` and `grants: []`), the sign-in routes, and attesting the device (`/v1/attest/*`);
- functions deployed with `open_to_pending_devices: true`, over `/v1/functions/{name}/invoke`, `/v1/invoke/…` and `/v1/functions/{name}/ws` ([Functions](/docs/developer/functions#open-to-pending-devices)).

Everything else, among it the account's devices and sessions, pub/sub, storage, cache, push, WebRTC and every other function, answers `403 DEVICE_PENDING_APPROVAL` with `device_id`.

An open function decides. `get_caller_device_state()` tells it the caller is `pending`; `get_caller_jwt_subject()` and `get_caller_device_id()` say who and which device. When the application's check passes, the function calls `approve_device(subject, device_id)`: the device becomes active, and the device's next `POST /v1/auth/refresh` returns a full session with `device_state: "active"`. The restricted access tokens it already holds stay restricted until they expire, so refresh right after the approval. When the check fails, `deny_device(subject, device_id)` revokes the device: its session, sockets and tokens stop on every gateway within ten seconds, and its key can never sign in again. Either call acts only in the function's own namespace, only on a pending device (approving an active one succeeds and changes nothing; denying one is refused), only while the policy is `function`, and is recorded in the audit log as `function:<name>`. Leaving the policy ends every restricted session at its next refresh (`DEVICE_PENDING`), and from then on `approve_device` and `deny_device` refuse. Until that refresh, the restricted access tokens already issued keep working for the rest of their life (at most 15 minutes), and with them the functions open to pending devices: close those functions, or let the tokens run out, if that matters to the application.

Who may approve is the application's code, not the gateway's: an open function that approves its own caller without a check lets any wallet signature add a device. Decide in the function what proves the request, for example a signed message from one of the account's active devices, which the function can verify, or the application's recovery secret.

Under `function` the namespace's functions are the only way a device is admitted, so device links are refused at every step with `403 DEVICE_LINK_FUNCTION_POLICY`: starting one (`POST /v1/auth/device` with `device_key`), approving one from a device (`/v1/auth/devices/approve`), and collecting its session (`/v1/auth/device/token`), a link started or approved before the policy was set included. A link would make its device active past the application's decision. Seedless linking is therefore not available under `function`: a new device signs in with the wallet and its own key, and waits for the application.

## Rolling it out

A gateway that predates devices knows nothing of the policy, of device-bound sign-in or of `device:` revocations. Set a session policy, and ship clients that bind devices, only once every gateway in the cluster runs this version. The same holds for `function`, which needs every gateway of the cluster and of the namespace on a release that has it (0.3.12 or later) before it is set: a gateway that predates it cannot read the policy, and answers `503` on sign-in and on the session and device routes for a namespace set to `function`; it refuses a restricted session's token outright; and a namespace gateway that predates it sees a restricted session proxied to it as no caller at all.

## Error codes

| Code | Means |
|---|---|
| `DEVICE_REQUIRED` | The namespace requires sessions bound to a device (403) |
| `DEVICE_KEY_INVALID` | The key is not a P-256 or Ed25519 public JWK, or is not the device the message names (400) |
| `DEVICE_SIGNATURE_INVALID` | The device's signature over the sign-in message does not verify (401) |
| `DEVICE_PROOF_REQUIRED` | A device-bound credential was presented without the device's proof (401) |
| `DEVICE_PROOF_INVALID` | The proof is malformed, reused, or not the device's (401) |
| `DEVICE_PROOF_CLOCK_SKEW` | The proof's time is more than 60 seconds from the gateway's clock; `server_time` is the gateway's clock (401) |
| `DEVICE_REVOKED` | The device presenting itself was revoked; its key can never hold a session again. `revocation` says who revoked it and carries the proof ([What a revoked device is told](#what-a-revoked-device-is-told)) (403) |
| `DEVICE_PENDING` | The device waits for another of the account's devices to approve it (403, or 202 on sign-in); under `function`, a pending device's refresh after the namespace left the policy |
| `DEVICE_PENDING_APPROVAL` | The session is a pending device's restricted session and this route or function is not open to it; `device_id` is the device (403) |
| `DEVICE_NOT_FOUND` | The account has no such device (404) |
| `DEVICE_KEY_TAKEN` | The key is enrolled for another account (403) |
| `DEVICE_USER_CODE_MALFORMED` | The user code is not the shape the gateway issues (400) |
| `DEVICE_LINK_FUNCTION_POLICY` | A device link (starting, approving or collecting one) in a namespace under the `function` policy, where the namespace's functions admit devices (403) |
| `DEVICE_LOGIN_MISMATCH` | The pending login is for another namespace or account, or is the other kind: a device link offered to a wallet, or a plain login to a device (400) |
| `POLICY_SWEEP_INCOMPLETE` | The policy is set, but revoking end users' existing keys stopped partway. Repeat the `PUT` (503) |
